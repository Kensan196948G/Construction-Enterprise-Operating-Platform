# AI 連携の設計（Phase 3 候補・OI-007 承認後に実装）

ステータス: Accepted（2026-08-07・ユーザー承認）／実装: v0.3.0 で要約機能をオフライン動作可能に実装

## 1. 目的と対象外

Phase 3 の AI 機能は、ポートフォリオ運用の「気づき」を補助するものに限定する。
v0.3.0 で「プロジェクト概要の要約」、v0.4.0 で「類似プロジェクト検出・リスク説明」、
v0.5.0 で「ベクトル類似検出（JSON 埋め込み・コサイン）と LLM 自然言語化」を
オフライン動作可能な形で実装した。
以下は実装時の基準と受入条件。

- 対象: プロジェクト概要の要約（v0.3.0 実装済み・オフライン/OpenAI 対応）、
  類似プロジェクト検出（v0.4.0 メタデータ類似度・v0.5.0 ベクトル類似度を追加）、
  停滞・リスクの説明（v0.4.0 ルールベース・v0.5.0 で LLM 自然言語化を追加）、
  レビュー優先度の提案
- 対象外: 承認値の自動上書き、関係性の自動確定、社外へのデータ送信を伴わない
  保証のない判断、個人情報の入力

## 2. データとプライバシー

- 入力は GitHub 由来の公開メタデータ＋管理者承認値（summary / lifecycle / importance /
  topics）に限定。README 本文・Issue/PR の本文・社内文書・個人情報は送信しない。
- 送信前に機密判定（キーワード＋手動レビュー）を必須とする。
- 社外 API を利用する場合、データ処理契約（DPA）と保存期間・学習利用可否を確認する。

## 3. アーキテクチャ（候補）

```text
Web/API → AI サービス（要約・分類・RAG） → 監査ログ（プロンプト要約・モデル・コスト）
                    ↓
         人による承認 UI（提案の確定・却下）
```

- 実装方式: 外部 API（OpenAI 等）またはセルフホストモデル。会社方針に応じて選択。
- RAG を導入する場合: 対象は公開 README の要約のみ（長期保存は設定で制限）。
- 検索・分類は既存の PostgreSQL 全文検索＋ベクトル拡張（pgvector）を検討。

### ベクトル類似の実装と pgvector 移行方針

- v0.5.0 現在: `project_embeddings` テーブル（JSON）＋Python コサイン類似。
  数十〜数百プロジェクト規模では十分な性能（全件比較・数 ms 程度）。
- 移行トリガー: プロジェクト数が 1,000 を超える、または類似検索の p95 が
  200ms を超える場合。
- 移行手順（将来）:
  1. Neon で `CREATE EXTENSION IF NOT EXISTS vector`
  2. `ALTER TABLE project_embeddings ADD COLUMN embedding vector(1536)`
  3. HNSW インデックス作成、既存 JSON 埋め込みを backfill
  4. クエリを `ORDER BY embedding <=> :vec LIMIT 5` へ変更（SQLAlchemy pgvector 型）
  5. 検証後、JSON 列を段階的に廃止

## 4. 信頼度・人の承認

- AI 出力には必ず「AI 提案・未確認」の表示と信頼度（0〜1）を付与。
- 台帳・関係性への反映は管理者の明示承認のみ（既存の楽観ロック・監査ログを利用）。
- モデル障害時は AI 機能を無効化し、既存の手動・ルール判定へフォールバック
  （フェイルオープンにしない）。

## 5. 費用と制限

- 月次費用上限を設定（例: 5,000 円/月・超過時は自動停止）。
- リクエスト/日・トークン/月のレート制限を実装し、Prometheus でコスト指標を監視。
- バッチ処理はオフピーク（深夜）に実行。

## 6. 監査

- 全 AI リクエストは「機能・モデル・入力要約・出力・コスト・成否」を監査ログへ記録。
- 個人情報・秘密情報の送信を検出した場合は即時遮断しアラート。

## 7. 受入条件（実装開始時）

1. OI-007 のユーザー承認（README 保存範囲・AI 利用可否）が得られている
2. 費用上限・データ送信範囲・モデル選択が承認されている
3. 監査・フォールバック・遮断の実装とテストが完了している
4. 既存機能（一覧・詳細・通知）に AI がない状態でも全機能が動作する
