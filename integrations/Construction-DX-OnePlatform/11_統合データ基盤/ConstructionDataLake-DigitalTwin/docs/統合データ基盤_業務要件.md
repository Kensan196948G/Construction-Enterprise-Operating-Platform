## 1. 部門概要と業務範囲

### 1.1 統合データ基盤の位置づけ

統合データ基盤は、全社11部門のシステムから生成されるデータを一元的に収集・蓄積・加工・提供する横断的なデータプラットフォームである。各部門システムが「業務の実行」を担うのに対し、本基盤は「データの流通と価値創出」を担う。

### 1.2 業務範囲

- **データ収集・統合**: 全社システムからのデータ収集、ETLパイプライン運用
- **データガバナンス**: データ品質管理、メタデータ管理、アクセス制御
- **データカタログ**: 全社データ資産の可視化・検索・利活用促進
- **マスタデータ管理（MDM）**: 全社共通マスタの一元管理・配信
- **データ分析基盤**: BI・AI/ML向けデータマート提供
- **MLOps**: AI/MLモデルのライフサイクル管理
- **デジタルツイン**: 建設現場・インフラの3Dデジタルモデル運用
- **API Gateway**: 全社データAPIの統合管理・提供
- **データレイク運用**: ストレージ階層管理、コスト最適化

## 2. ETLパイプライン運用業務

### 2.1 データ収集パイプライン管理

#### 2.1.1 業務概要

全社11部門のシステムからデータを定期的・リアルタイムに収集し、データレイクに蓄積する。

#### 2.1.2 データソース一覧

| ソースシステム | データ種別 | 取得方式 | 頻度 |
|---------------|-----------|---------|------|
| 経営ダッシュボード | KPI集計値、予算実績 | REST API | 日次 |
| 建設CRM | 案件情報、入札データ | CDC (Change Data Capture) | リアルタイム |
| 施工管理システム | 工程・原価・写真・IoTセンサー | Kafka Stream | リアルタイム |
| 安全品質ガバナンス | ヒヤリハット、パトロール、NCR | REST API | 日次 |
| 技術ナレッジBIM基盤 | 技術文書、BIM/CIMモデル | ファイル連携（S3互換） | イベント駆動 |
| 企業運営基盤 | 会計データ、人事データ、契約 | バッチETL（dbt） | 日次 |
| 調達資材管理 | 発注・在庫・単価データ | CDC | リアルタイム |
| 船舶運航管理 | AIS/GPS位置情報、燃料データ | MQTT/Kafka | リアルタイム |
| ITSM基盤 | インシデント、CMDB、ログ | REST API / Syslog | リアルタイム |
| DeskNet's NEO | ワークフロー承認データ | REST API連携 | イベント駆動 |
| IoTセンサー | 温湿度、振動、粉塵、騒音 | MQTT → Kafka | リアルタイム |
| 外部データ | 気象、地図、CCUS、CORINS | REST API | 定期バッチ |

#### 2.1.3 ETLパイプライン設計要件

- **オーケストレーション**: Apache Airflow によるDAG管理
  - DAG定義はGitリポジトリで管理（GitOps）
  - 依存関係の自動解決、リトライポリシー設定
  - SLA監視（遅延アラート自動通知）
- **データ変換**: dbt (Data Build Tool) による変換レイヤー
  - Bronze層（Raw）→ Silver層（Cleansed）→ Gold層（Aggregated）の3層モデル
  - dbtテスト（not_null, unique, accepted_values, relationships）自動実行
  - dbt docsによる変換ロジックのドキュメント自動生成
- **ストリーム処理**: Apache Kafka + Kafka Streams
  - IoTセンサーデータのリアルタイム処理
  - CDC（Debezium）によるDB変更のリアルタイム連携
  - Schema Registry（Avro/Protobuf）によるスキーマ管理

#### 2.1.4 パイプライン監視要件

| 監視項目 | 閾値 | アラート先 |
|---------|------|-----------|
| DAG実行失敗 | 1回以上 | Slack + メール即時通知 |
| DAG遅延 | SLA超過10分以上 | Slack通知 |
| データ品質テスト失敗 | dbtテスト1件以上失敗 | Slack + Jiraチケット自動起票 |
| Kafkaコンシューマーラグ | 10,000メッセージ以上 | Grafanaアラート |
| ストレージ使用量 | 80%以上 | 週次レポート + アラート |
| ETL処理時間 | 前回比200%以上 | 自動調査トリガー |

## 3. データガバナンス業務

### 3.1 データ品質管理

#### 3.1.1 品質ルール定義

| 品質次元 | チェック内容 | 自動化方式 |
|---------|------------|-----------|
| 完全性（Completeness） | 必須フィールドのNULL率 | dbt test + Great Expectations |
| 一意性（Uniqueness） | 主キー重複チェック | dbt unique test |
| 正確性（Accuracy） | 値域チェック、フォーマット検証 | Great Expectations Suite |
| 一貫性（Consistency） | テーブル間整合性、外部キー参照 | dbt relationships test |
| 適時性（Timeliness） | データ鮮度（最終更新からの経過時間） | カスタムSQLチェック |
| 妥当性（Validity） | ビジネスルール適合性 | カスタムバリデーション |

#### 3.1.2 データ品質スコアリング

- 各データセットに対して品質スコア（0-100）を自動算出
- スコア70未満のデータセットは利用制限（警告表示）
- スコア50未満のデータセットは利用停止（自動遮断）
- 月次データ品質レポートを全社配信

#### 3.1.3 データリネージ管理

- dbt + OpenLineage によるデータ変換の系譜追跡
- ソースからBIレポートまでのEnd-to-Endリネージ可視化
- カラムレベルのリネージ追跡
- 影響分析（上流変更時の下流影響範囲特定）

### 3.2 データアクセス制御

#### 3.2.1 アクセスポリシー

| レベル | 対象データ | アクセス権限 |
|-------|-----------|------------|
| 公開（Public） | 気象データ、公共工事情報 | 全社員参照可 |
| 社内限定（Internal） | 工程データ、技術文書 | 社員のみ参照可 |
| 部門限定（Confidential） | 原価データ、人事データ | 所属部門のみ |
| 機密（Restricted） | 経営戦略、入札価格 | 特定権限者のみ |

#### 3.2.2 アクセス制御実装

- Entra ID グループベースのRBAC（Role-Based Access Control）
- Apache Ranger によるデータレイクレベルの細粒度アクセス制御
- カラムレベルマスキング（個人情報、原価情報）
- 行レベルセキュリティ（部門・プロジェクト単位）
- アクセスログの完全記録・監査対応

### 3.3 データ保持・廃棄ポリシー

| データ分類 | 保持期間 | 廃棄方式 | 根拠法令 |
|-----------|---------|---------|---------|
| 会計データ | 10年 | 論理削除後物理削除 | 電子帳簿保存法 |
| 契約データ | 10年 | 論理削除後物理削除 | 建設業法 |
| 施工記録 | 永年 | アーカイブ（Cold Storage） | 品確法 |
| 安全記録 | 5年 | 論理削除後物理削除 | 労働安全衛生法 |
| 人事データ | 退職後5年 | 完全削除（暗号鍵破棄） | 個人情報保護法 |
| IoTセンサー（Raw） | 1年 | 自動削除（TTL） | 社内規定 |
| IoTセンサー（集計済） | 5年 | Cold Storageへ移行 | 社内規定 |
| BIM/CIMモデル | 永年 | Glacier互換ストレージ | i-Construction要件 |

## 4. データカタログ管理業務

### 4.1 メタデータ管理

#### 4.1.1 管理対象メタデータ

- **技術メタデータ**: テーブル定義、カラム型、パーティション情報、インデックス
- **ビジネスメタデータ**: データオーナー、説明、分類タグ、利用用途
- **運用メタデータ**: 更新頻度、最終更新日時、データ件数、サイズ
- **品質メタデータ**: 品質スコア、テスト結果、異常検知履歴

#### 4.1.2 データカタログ機能要件

- **全文検索**: Elasticsearch + Kuromoji による日本語対応検索
- **タグ分類**: 部門タグ、業務タグ、機密レベルタグの付与・検索
- **データプレビュー**: サンプルデータ（最大100行）の即座表示
- **利用状況可視化**: データセットごとのアクセス頻度・利用者数ダッシュボード
- **データリクエスト**: 新規データ要求のワークフロー管理
- **用語集（Glossary）**: 全社共通のビジネス用語定義管理

#### 4.1.3 自動メタデータ収集

- dbt manifest.json からのテーブル・カラム情報自動取得
- Airflow DAG定義からのパイプライン情報自動取得
- PostgreSQL information_schema からのスキーマ情報自動同期
- Kafka Schema Registry からのイベントスキーマ自動取得

### 4.2 データセット公開管理

#### 4.2.1 公開フロー

1. データオーナーが公開申請（メタデータ・品質基準入力）
2. データスチュワードがレビュー（品質スコア確認、アクセス制御設定）
3. 承認後、データカタログに自動登録
4. 利用者への通知（Slack/メール）

#### 4.2.2 データセット評価

- 利用者によるレーティング（5段階）
- 利用者コメント・改善要望の収集
- 人気データセットランキング（月次）
- 未利用データセットの定期レビュー・廃止検討

### 5.2 MDM運用要件

#### 5.2.1 マスタ同期方式

- **Golden Record方式**: 各ソースシステムのデータを統合し、信頼性の高い単一レコードを生成
- **双方向同期**: マスタ変更は管理部門から配信、各システムのローカル変更は承認後マスタへ反映
- **同期プロトコル**: REST API（プル型）+ Kafkaイベント（プッシュ型）の併用
- **競合解決**: タイムスタンプベース + 管理部門優先ルール

#### 5.2.2 マスタ変更管理

- 変更申請 → 管理部門承認 → テスト環境反映 → 本番反映の4段階フロー
- 全変更履歴の完全保持（temporal table）
- 変更影響分析（依存システム一覧の自動表示）
- 大量変更時のバッチ処理対応（CSV一括インポート）

#### 5.2.3 名寄せ・データクレンジング

- 協力会社マスタの名寄せ（類似名称の統合提案、AI支援）
- 住所正規化（日本郵便APIとの連携）
- 電話番号フォーマット統一
- 法人番号（13桁）との照合による企業情報精度向上

## 9. API Gateway管理業務

### 9.1 API管理要件

#### 9.1.1 API Gateway機能

- **認証・認可**: OAuth 2.0 / JWT（Entra ID連携）
- **レート制限**: 部門別・アプリケーション別のAPI呼び出し制限
- **APIバージョニング**: URL パスベース（/api/v1/, /api/v2/）

## 10. データレイクストレージ運用業務

### 10.1 ストレージ階層管理

#### 10.1.1 ストレージ階層設計

| 階層 | 用途 | ストレージ種別 | アクセス頻度 | コスト |
|-----|------|--------------|------------|-------|
| Hot | 直近1ヶ月のアクティブデータ | SSD（NVMe） | 高頻度 | 高 |
| Warm | 1ヶ月〜1年のデータ | HDD（RAID） | 中頻度 | 中 |
| Cold | 1年〜5年のアーカイブ | オブジェクトストレージ | 低頻度 | 低 |
| Archive | 5年以上の長期保管 | Glacier互換 | 極低頻度 | 最低 |

#### 10.1.2 ライフサイクルポリシー

- データ分類に基づく自動階層移行ルール
- アクセス頻度に基づく動的階層最適化
- 保持期間超過データの自動アーカイブ/削除
- ストレージコスト月次レポート

### 10.2 バックアップ・災害復旧

#### 10.2.1 バックアップ要件

| 対象 | バックアップ方式 | 頻度 | 保持期間 | RPO | RTO |
|-----|----------------|------|---------|-----|-----|
| PostgreSQL | WALアーカイブ + ベースバックアップ | 継続的 + 日次 | 30世代 | 5分 | 1時間 |
| TimescaleDB | 連続アーカイブ | 継続的 | 14日 | 5分 | 2時間 |
| Elasticsearch | スナップショット | 日次 | 7世代 | 24時間 | 4時間 |
| オブジェクトストレージ | クロスリージョンレプリケーション | リアルタイム | N/A | 0 | 即時 |
| Kafka | ミラーメーカー | リアルタイム | 7日 | 数秒 | 30分 |
| BIM/CIMモデル | バージョン管理 + 差分バックアップ | 日次 | 永年 | 24時間 | 8時間 |

#### 10.2.2 災害復旧計画

- DR環境は別リージョン（Azure East Japan ⇔ West Japan）
- 重要データ（PostgreSQL、Kafka）はリアルタイムレプリケーション
- 年2回のDR訓練実施（フェイルオーバー・フェイルバック）
- RTOに基づく復旧優先順位の定義
