## 📌 1. 目的と適用範囲

### 1.1 目的

本文書は ISO 27001:2022 附属書 A.8.1 および A.8.2 に基づき、Construction-DX-OnePlatform が保有・処理するすべての情報資産を識別・分類・管理することを目的とする。情報資産の機密性・完全性・可用性（CIA トライアド）を明確にし、資産ライフサイクル全体を通じて適切な保護措置を確保する。

### 1.2 適用範囲

- **対象**: 本プラットフォームを構成する全11部門のシステムコンポーネント（APIサーバ、フロントエンド、データベース、Redis、MinIO、Elasticsearch を含む）
- **対象外**: 個人所有デバイス（BYODポリシー参照）、外部SaaSの内部データ（別途リスクアセスメントで管理）

### 1.3 適用規格

| 規格           | 管理策 | 内容                   |

| ISO 27001:2022 | A.8.1  | 情報資産のインベントリ |

## 📋 2. 分類基準

### 2.1 機密性（Confidentiality）

| 分類 | ラベル | 定義                                       | 取扱例                         |
| ---- | ------ | ------------------------------------------ | ------------------------------ |
| C3   | 極秘   | 漏洩により重大な経営・法的損害が生じる     | 個人情報、認証秘密鍵、財務原本 |
| C2   | 社外秘 | 社内限定。漏洩により競争上の不利益が生じる | 内部設計書、工事単価、契約条件 |
| C1   | 一般   | 公開可能または社内自由閲覧                 | 公開API仕様、一般広報資料      |

### 2.2 完全性（Integrity）

| 分類 | ラベル | 定義                                       |
| ---- | ------ | ------------------------------------------ |
| I3   | 高     | 改ざんにより業務停止または法令違反が生じる |
| I2   | 中     | 改ざんにより業務品質に重大な影響が生じる   |
| I1   | 低     | 改ざんの影響が軽微かつ回復可能             |

### 2.3 可用性（Availability）

| 分類 | ラベル | 定義                           | RTO目安    |
| ---- | ------ | ------------------------------ | ---------- |
| A3   | 高     | 停止により即座に業務不能となる | 1時間以内  |
| A2   | 中     | 停止により業務に支障が出る     | 4時間以内  |
| A1   | 低     | 計画停止可能な補助システム     | 24時間以内 |

## 📌 5. 保管場所と廃棄手順

### 5.1 保管場所分類

| 保管区分                    | 対象資産                                    | セキュリティ要件                                       |
| --------------------------- | ------------------------------------------- | ------------------------------------------------------ |
| コンテナ（Docker）          | APIサーバ、フロントエンド、各種ミドルウェア | TLS必須、ネットワーク分離、コンテナイメージ署名        |
| クラウドDB（PostgreSQL）    | 各部門DB、統合DWH                           | 暗号化（at-rest AES-256）、VPC内限定、自動バックアップ |
| Redisクラスタ               | セッション・キャッシュ                      | 認証必須（AUTH）、TLS、保持期間設定（TTL）             |
| MinIOオブジェクトストレージ | 図面、文書、バイナリ                        | バケットポリシー、サーバサイド暗号化（SSE-S3）         |
| Elasticsearchクラスタ       | 全文検索インデックス                        | 認証必須、フィールドレベルセキュリティ                 |
| GitHub Secrets              | CI/CD秘密鍵、APIトークン                    | 環境変数として注入、ログ出力禁止                       |
| ローカルファイルシステム    | 一時ファイル、ログ                          | アクセス制御、定期削除（30日）                         |

### 5.2 廃棄手順

#### 5.2.1 電子情報の廃棄

廃棄は必ず資産オーナーの承認を得た後に実施すること。廃棄後は廃棄台帳（`reports/audit/disposal_log.md`）に記録する。

```bash
# PostgreSQL: テーブルデータ完全消去
DROP TABLE target_table CASCADE;
VACUUM FULL ANALYZE;

# MinIOオブジェクト: バケット内オブジェクト削除
mc rm --recursive --force minio/bucket-name/path/

# MinIOバケット自体を削除する場合
mc rb --force minio/bucket-name

# Redisキー削除（パターン指定）
redis-cli -a $REDIS_PASSWORD --scan --pattern "session:*" | xargs redis-cli -a $REDIS_PASSWORD DEL

# Dockerイメージ廃棄
docker rmi --force image_id
docker system prune -f --volumes

# Elasticsearch インデックス削除
curl -X DELETE "https://elasticsearch:9200/index-name" \
  -H "Authorization: Bearer $ES_TOKEN"
```

#### 5.2.2 廃棄記録様式

廃棄実施後、以下の情報を廃棄台帳に記録する。

| 記録項目               | 内容例                                       |
| ---------------------- | -------------------------------------------- |
| 廃棄日時               | 2026-06-01 14:30 JST                         |
| 廃棄対象資産ID         | ASSET-0202                                   |
| 廃棄方法               | DB DROP + VACUUM / mc rm / docker rmi        |
| 廃棄実施者             | yamamoto.k（IT-DX部門）                      |
| 承認者（資産オーナー） | 営業本部長 sato.m                            |
| 廃棄証明               | コマンド出力ログまたはスクリーンショット添付 |
| 次回確認日             | 廃棄後30日（残存確認）                       |

#### 5.2.3 物理媒体（ハードウェア）の廃棄

物理媒体を廃棄する場合は、以下のいずれかの方法を採用する。

1. データ完全消去（DoD 5220.22-M 準拠、3回上書き）
2. 物理的破壊（シュレッダーまたは専門業者委託）
3. 認定廃棄業者への委託（廃棄証明書を取得・7年保管）

#### 5.2.4 暗号鍵の廃棄・ローテーション

```bash
# JWT秘密鍵のローテーション（shared-auth）
# 1. 新鍵生成
openssl rand -hex 64 > /tmp/new_jwt_secret.txt

# 2. Secretsへ登録（ダウンタイムなし移行）
kubectl create secret generic jwt-secret \
  --from-file=secret=/tmp/new_jwt_secret.txt \
  --dry-run=client -o yaml | kubectl apply -f -

# 3. 旧鍵の無効化確認後、削除
kubectl delete secret old-jwt-secret

# 4. 廃棄台帳へ記録
echo "$(date -u) JWT_KEY rotated by $(whoami)" >> reports/audit/key_rotation_log.txt

# 一時ファイルの安全削除
shred -vuz /tmp/new_jwt_secret.txt
```

| 暗号鍵管理       | 所管する暗号鍵・APIトークンのローテーションを年次で実施する                     |
