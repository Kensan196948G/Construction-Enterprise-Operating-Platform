## 📌 1. 目的と適用範囲

### 1.1 目的

本手順書は ISO 20000-1:2018 § 8.2 に基づき、Construction-DX-OnePlatform における問題管理プロセスを定義する。インシデントの再発防止・根本原因の除去・既知エラーの管理を通じ、サービス品質の継続的改善を実現することを目的とする。

問題管理はインシデント管理と明確に区分する。インシデント管理はサービス復旧を優先するのに対し、問題管理は根本原因の特定と恒久対策の実施に焦点を当てる。

### 1.2 適用範囲

- 対象: 本プラットフォームを構成する全11部門のシステムコンポーネント
- 対象インシデント: CRITICAL / HIGH 重大度インシデント、または同一事象が月2回以上発生したもの
- 担当組織: 10_IT-DX部門（ITSM運用チーム）、各部門システム担当

### 1.3 適用規格

| 規格             | 条項   | 内容                                     |
| ---------------- | ------ | ---------------------------------------- |
| ISO 20000-1:2018 | § 8.2  | 問題管理                                 |

## 📋 2. 問題管理プロセスフロー

```
インシデント発生
     │
     ▼
【インシデント管理】
  - サービス復旧を最優先
  - 暫定対処（ワークアラウンド）を適用
  - docs/RUNBOOK.md §5 インシデント対応に従い対処
     │
     ▼ CRITICAL/HIGH または再発インシデント
【問題登録】
  - 問題チケット起票（GitHub Issues / ITSMツール）
  - ラベル: problem / P1|P2|P3
  - 担当: IT-DX部門 問題管理担当者
     │
     ▼
【根本原因分析（RCA）】
  - 5-Why 法または フィッシュボーン（特性要因図）を用いる
  - 分析期限: CRITICAL=48時間 / HIGH=5営業日 / MEDIUM=10営業日
     │
     ▼
【既知エラー（Known Error）判定】
  - 根本原因が特定済みで恒久解決策がない → 既知エラーとして KEDB に登録
  - 暫定対処（ワークアラウンド）を KEDB に記録しインシデント担当者が参照できるようにする
     │
     ├── 解決策あり ──→ 【変更管理】→ 実装 → テスト → クローズ
     │
     └── 解決策なし ──→ 【既知エラー管理】→ 監視継続 → 次サイクルで再評価
                              │
                              ▼
                       【問題クローズ】
                         - 解決確認・再発なし確認（観察期間: 30日）
                         - 問題レポート最終化
                         - KEDB から削除または「解決済み」に更新
```

### 2.1 プロセスステップ詳細

| ステップ             | 実施者                          | 期限                             | 成果物                        |
| -------------------- | ------------------------------- | -------------------------------- | ----------------------------- |
| 問題登録             | インシデント担当 / 問題管理担当 | インシデントクローズ後24時間以内 | 問題チケット                  |
| 初期分類・優先度設定 | 問題管理担当                    | 登録後4時間以内                  | 優先度・担当アサイン          |
| 根本原因分析（RCA）  | 技術担当（部門横断）            | 優先度別期限参照                 | RCAレポート                   |
| 解決策立案           | 技術担当・IT-DX部門             | RCA完了後5営業日                 | 変更要求（CR）または KEDB登録 |
| 恒久解決の実装       | 開発チーム / DevOps             | 変更管理スケジュール準拠         | デプロイ・テスト証跡          |
| 問題クローズ         | 問題管理担当                    | 解決確認後30日観察期間満了後     | クローズレポート              |

## 📌 4. 根本原因分析（RCA）手順

### 4.1 5-Why 法

5-Why 法は、「なぜ（Why）」を繰り返すことで表面的な症状から根本原因へ掘り下げる手法である。

**適用場面**: 単一障害要因が疑われる場合、比較的シンプルな構成のシステム障害

**実施手順**:

1. 観察された問題（症状）を明確に記述する
2. 「なぜその問題が発生したか？」を問い、直接原因を特定する
3. ステップ2で特定した原因に対して再度「なぜ？」を問う
4. 根本原因（制度・プロセス・設計上の欠陥）に到達するまで繰り返す（通常5回程度）
5. 根本原因に対する是正措置を立案する

**記録様式**:

```
問題: APIゲートウェイが間欠的に503を返す

Why 1: なぜ503が発生したか？
  → バックエンドサービスへの接続タイムアウトが発生した

Why 2: なぜタイムアウトが発生したか？
  → データベース接続プールが枯渇した

Why 3: なぜ接続プールが枯渇したか？
  → 長時間実行クエリがコネクションを占有した

Why 4: なぜ長時間クエリが発生したか？
  → インデックスが未作成の列に対してフルスキャンが走った

Why 5: なぜインデックスが作成されていなかったか？
  → 新機能デプロイ時のマイグレーションレビューでインデックス設計が漏れた

根本原因: デプロイ前のマイグレーションレビュープロセスにインデックス設計確認が含まれていない
是正措置: デプロイゲートチェックリストにDBインデックス設計レビューを追加する
```

### 4.2 フィッシュボーン（特性要因図）

フィッシュボーン分析は、複数の要因カテゴリから問題の原因を体系的に整理する手法である。

**適用場面**: 複数要因が複合している複雑な障害、ネットワーク・セキュリティ・人的要因が絡む事象

**分析カテゴリ（IT障害向け）**:

| カテゴリ            | 確認観点の例                                             |
| ------------------- | -------------------------------------------------------- |
| 人（People）        | 操作ミス、スキル不足、引継ぎ漏れ、疲労・集中力低下       |
| プロセス（Process） | 手順書の不備、レビュー漏れ、承認フローの欠如             |
| 技術（Technology）  | バグ、設定ミス、キャパシティ不足、バージョン非互換       |
| 環境（Environment） | インフラ障害、ネットワーク不安定、外部依存サービスの障害 |
| 材料（Materials）   | 不正なデータ入力、外部データ品質、ライブラリの脆弱性     |
| 測定（Measurement） | 監視設定の漏れ、アラート閾値の不適切さ、ログ不足         |

**実施手順**:

```
1. 魚の頭（右端）に「問題（結果）」を記載する
2. 中心の骨（主幹線）を水平に引く
3. 大骨として上記6カテゴリを斜めに伸ばす
4. 各カテゴリについてチームでブレインストーミングし、要因を小骨として記入する
5. 要因の中から最も影響度が高い根本原因候補を絞り込む
6. データ・ログ・証跡で候補を検証し、根本原因を確定する
```

### 4.3 RCA実施にあたっての注意事項

- RCA は「犯人探し」ではなく「プロセス・システムの改善」を目的とすること
- 分析には関連部門の担当者を横断的に招集すること
- 仮説は必ずログ・モニタリングデータで裏付けること
- 結論は1つの根本原因に絞り込むのではなく、複数の寄与因子を記録してよい

## 📋 5. 既知エラーデータベース（KEDB）管理方針

### 5.1 KEDB の目的

既知エラーとは、根本原因が特定済みであるが恒久解決策がまだ実装されていない問題を指す。KEDB に登録することで、同様のインシデント発生時にインシデント担当者が素早く暫定対処を参照できるようにする。

### 5.2 KEDB 登録基準

以下のいずれかに該当する場合、問題を既知エラーとして KEDB に登録する。

- 根本原因が特定済みで、恒久解決策の実装に2週間以上かかることが確定した
- 再発リスクがあり、インシデント担当者がワークアラウンドを知っておく必要がある
- 恒久解決がビジネス上の理由でリスク受容（Known Error として管理継続）となった

### 5.3 KEDB レコード形式

````markdown
## KEDB-2026-001

**登録日**: 2026-06-01
**対応問題チケット**: PROB-2026-001
**影響サービス**: 営業API（Backend 02 / Port 8002）
**根本原因**: PostgreSQL接続プール枯渇（インデックス未設定クエリによる長時間ロック）

### 症状

- API Gateway が間欠的に503を返す
- 発生条件: 月次バッチ実行時間帯（毎月第1月曜 03:00-04:00 JST）

### 暫定対処（ワークアラウンド）

```bash
# 長時間クエリの強制終了
psql -U postgres -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity
  WHERE state = 'active' AND query_start < now() - interval '5 minutes';"

# 接続プールのリセット（アプリ再起動不要）
curl -X POST http://localhost:8002/admin/db/pool/reset \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```
````

### 恒久解決策（予定）

- `customer_orders` テーブルに複合インデックス追加
- 対応 CR: CR-2026-015
- 実装予定: 2026-06-15

**ステータス**: Open（解決策実装待ち）  
**更新日**: 2026-06-01  
**担当者**: IT-DX部門 インフラチーム

```

### 5.4 KEDB の保管場所と管理

- **保管場所**: `reports/audit/kedb/` ディレクトリ配下に Markdown ファイルで管理
- **命名規則**: `KEDB-YYYY-NNN.md`
- **インデックス**: `reports/audit/kedb/INDEX.md` で全登録エントリを一覧管理
- **参照権限**: 全IT担当者（読取可）、問題管理担当者のみ更新可
- **定期レビュー**: 月次で全 KEDB エントリを見直し、解決済みは「Closed」に更新する

### 5.5 KEDB クローズ基準

- 恒久解決策の実装とテスト完了
- 30日間の観察期間中に同一症状が再発しないこと
- 問題管理担当者によるクローズ承認

## 🔧 6. ITSM連携（10_IT-DX部門）

### 6.1 連携インターフェース

10_IT-DX部門（`/10_IT-DX部門/`）は本プラットフォームのITSM運用の中核部門として、以下の役割を担う。

| 役割 | 担当 | 詳細 |
|------|------|------|
| 問題管理担当者 | IT-DX部門 運用チーム | 問題チケット管理、RCA調整、KEDB管理 |
| 変更管理窓口 | IT-DX部門 変更管理担当 | 問題解決に伴う変更要求の受付・スケジューリング |
| サービスオーナー | IT-DX部門長 | 月次問題管理レポートの承認 |

### 6.2 インシデント管理との連携フロー

```

インシデント管理（docs/RUNBOOK.md §5）
│
│ CRITICAL/HIGH インシデント、または再発インシデント
▼
問題登録（本手順書 §2）
│
│ KEDB 参照情報をインシデント担当者へフィードバック
▼
暫定対処情報（KEDB）の共有
│
│ 根本原因特定後
▼
変更管理プロセス（DEPLOYMENT.md 参照）
│
│ 恒久解決実装後
▼
問題クローズ → 月次レポートへ集約

````

### 6.3 エスカレーション基準

| 状況 | エスカレーション先 | 期限 |
|------|-----------------|------|
| P1問題のRCAが48時間で完了しない | IT-DX部門長 → CTO | 48時間超過時点 |
| 恒久解決策の実装が3ヶ月以上遅延 | IT-DX部門長 → 経営企画部 | 3ヶ月超過時点 |
| セキュリティ関連の問題（脆弱性起因） | Security担当 → CISO | 即時 |
| 個人情報に影響するインシデントに起因する問題 | CISO → 個人情報保護責任者 | 24時間以内 |

### 6.4 他ツール・システムとの統合

```bash

gh issue create \
  --title "[PROB] ${INCIDENT_TITLE}" \
  --label "problem,P${PRIORITY}" \
  --body "$(cat problem_template.md)" \

# 関連インシデントチケットとのリンク
gh issue edit PROB_ISSUE_NUMBER \
  --add-label "linked-incident:INC-${INCIDENT_ID}"
````

## 📊 7. 問題管理KPIと月次レポート

### 7.1 問題管理KPI

| KPI                          | 定義                                              | 目標値                | 測定頻度 |
| ---------------------------- | ------------------------------------------------- | --------------------- | -------- |
| 問題登録率                   | CRITICAL/HIGHインシデントのうち問題チケット起票率 | 100%                  | 月次     |
| RCA完了率                    | 期限内にRCAが完了した問題の割合                   | ≥ 90%                 | 月次     |
| 平均解決時間（MTTR-Problem） | 問題登録からクローズまでの平均日数                | P1: ≤30日 / P2: ≤60日 | 月次     |
| 再発率                       | クローズ後30日以内に同一問題が再発した割合        | ≤ 5%                  | 月次     |
| KEDB活用率                   | インシデント対応でKEDBが参照された割合            | ≥ 70%                 | 月次     |
| 未解決P1問題数               | 30日以上オープンのP1問題数                        | 0                     | 週次     |

### 7.2 月次問題管理レポート様式

月次レポートは毎月第1営業日までに作成し、IT-DX部門長の承認を得ること。保管先: `reports/audit/problem_mgmt_YYYY-MM.md`
