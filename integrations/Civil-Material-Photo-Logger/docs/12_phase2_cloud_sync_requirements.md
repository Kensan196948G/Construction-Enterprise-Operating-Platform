# Phase 2 要件定義書: クラウド同期・多人数運用（案）

> 位置づけ: 統合評価・改善報告書（docs/11）§9 ロードマップ Phase 2 の詳細要件定義（ドラフト）
> 最終更新: 2026-08-12
> 状態: **設計検討中（未実装・未承認）** — 本機能の実装判断は経営層・IT/DX部門の承認後

---

## 1. 背景と目的

現行アプリは完全オフライン・端末内保存のため、以下の課題がある。

1. 600名規模での記録共有・一元管理ができない（バックアップファイルの受け渡しのみ）。
2. 現場・本社・経営層・協力会社の役割（RBAC）と監査ログがない。
3. 検収・承認フローが人が介在するステータス操作のみ。
4. 公共工事の成果品対応（電子小黒板・CALS/EC XML・改ざん検知）の基盤がない。
5. 端末紛失・故障時の組織的復旧が人依存。

本要件は、**オフライン現場運用の強みを維持したまま**、クラウド同期・権限・監査を
追加するための設計方針を定める。実行環境は利用前提の「検証・公開基盤は Cloudflare、
DB 正本は Neon PostgreSQL、認証は Microsoft Entra ID、共有は SharePoint Online」に従う。

## 2. 適用範囲と対象外

### 2.1 対象（Phase 2 スコープ）

- 記録・写真のクラウド同期（オフラインキュー方式）
- Entra ID 認証とロール（現場担当 / 現場監督 / 資材担当 / IT・DX管理者 / 経営層閲覧）
- 操作監査ログ（作成・編集・削除・共有・承認・権限変更）
- 検収・承認フロー（ステータス遷移のルール化と通知）
- 案件・材料マスタの同期（表記揺れ・誤入力の低減）
- バックアップの組織的集約（端末→クラウド）
- Web 閲覧・集計画面（本社・経営層向け・読み取り専用）

### 2.2 対象外（Phase 2 では実施しない）

- 公共工事成果品対応（電子小黒板・CALS/EC XML・改ざん検知）→ **Phase 4 の別プロジェクトとして要件化**
- リアルタイム共同編集（同時編集は最終書き込み優先＋競合通知まで）
- AI 機能（RAG 検索・自動分類等）→ Phase 3
- Android / PWA → Phase 3
- オンプレミス（Windows Server）側での常時稼働サーバー

## 5. アーキテクチャ（初期案）

```text
現場端末 (iOS)                Cloudflare                Neon PostgreSQL
┌──────────────────┐   HTTPS   ┌─────────────────┐  ┌──────────────────┐
│ アプリ(既存+同期層)│ ───────▶ │ Workers API      │─▶│ records / photos │
│ オフラインキュー  │ ◀─────── │ ・認証(Entra ID) │  │ projects         │
│ ローカルDB(既存)  │           │ ・RBAC・監査ログ  │  │ materials        │
└──────────────────┘           │ ・同期API        │  │ audit_logs       │
                              └────────┬────────┘  └──────────────────┘
                                       │
                        ┌──────────────▼──────────────┐
                        │ Cloudflare R2 (写真オブジェクト)│
                        └─────────────────────────────┘
```

### 5.1 構成要素

| 要素 | 技術（案） | 役割 |
|---|---|---|
| 認証 | Microsoft Entra ID（OAuth2 / PKCE） | 社員は既存ID、協力会社はゲストIDで SSO |
| API | Cloudflare Workers（TypeScript） | REST API（同期・検索・集計・管理） |
| メインDB | Neon PostgreSQL | 記録・マスタ・監査ログ・権限（リレーショナル正本） |
| 写真 | Cloudflare R2（S3互換） | JPEG オブジェクト保存（DB はメタデータのみ） |
| Web 閲覧 | Cloudflare Pages | 本社・経営層向けダッシュボード（読み取り） |
| 通知 | Webhook → Teams / メール（Exchange Online） | 検収依頼・競合・バックアップ通知 |
| 監視 | Workers のログ＋Neon のメトリクス | エラー率・レイテンシ・同期失敗の監視 |

### 5.2 オフライン同期プロトコル（案）

1. 端末はローカル保存（現行方式）を維持し、操作ログ（変更イベント）をキューへ追記。
2. 通信回復時（または手動）に、キューを時系列で API へ送信。
3. API は変更イベントを受信順に適用し、**updatedAt の新しい方を優先**。
4. 同一レコードで競合（両者が未同期の変更を持つ）が発生した場合は `conflict` 状態にして
   利用者へ通知。後から選んだ方を正として同期（自動上書きはしない）。
5. 写真はまず端末でアップロードし、成功後に記録メタデータを更新（部分失敗の巻き戻しが不要）。
6. 同期対象は「自分の案件＋共有された案件」のみ。削除は論理削除（`deleted_at`）で同期し、
   監査ログを残す。

### 5.3 データモデル（初期案）

| テーブル | 主な列 | 備考 |
|---|---|---|
| `projects` | id, project_code, name, organization_id, archived_at | 案件マスタ |
| `materials` | id, name, category, unit, organization_id | 材料マスタ |
| `records` | id, project_id, material_id?, quantity, unit, storage_place, memo, transaction_type, inspection_status, needs_review, captured_at, location, created_by, updated_by, deleted_at, sync_version | 現行 MaterialRecord を拡張 |
| `photos` | record_id, file_name, storage_key, sha256, taken_at, width, height | R2 キーとハッシュ |
| `audit_logs` | id, actor_id, action, target_type, target_id, before, after, ip, created_at | 改ざん防止のため追記のみ |
| `user_roles` | user_id, role, project_id?, granted_by, granted_at | 案件単位ロール |
| `sync_events` | id, device_id, record_id, event_type, payload_hash, applied_at | 同期イベントの重複排除 |

**原則**: 現行アプリの `MaterialRecord` のフィールドは維持し、`syncStatus` を
`.pendingUpload` / `.synced` / `.conflict` へ拡張する（既存データは後方互換）。

## 7. セキュリティ・監査要件

1. 認証: Entra ID（OAuth2 + PKCE）。端末紛失時は条件付きアクセスで失効可能。
2. 認可: API 側で案件単位の RBAC を強制（クライアントだけでなくサーバーで検証）。
3. 通信: TLS 1.2 以上。写真アップロードは署名付き URL。
4. 保存: DB は PostgreSQL の暗号化、R2 はオブジェクト暗号化。写真の公開アクセス禁止。
5. 監査: `audit_logs` は追記のみ（UPDATE/DELETE 禁止）。操作者・端末・時刻・変更前後を記録。
6. 監査ログの保存期間: 最低3年（会社規定に合わせて調整）。
7. プライバシー: 位置情報・写真は記録データと同様に権限フィルタ。外部への転送はしない。
8. 秘密情報: Workers のシークレット（Neon接続文字列等）は環境変数/シークレット管理に限定し、
   Git に保存しない（既存の Gitleaks CI で検出）。
9. プロンプトインジェクション等の AI 関連は Phase 3 で設計（本要件では API 入力の検証を徹底）。

## 10. 受入条件（Phase 2 完了時の定義）

1. 電波のない環境で記録し、復旧後に自動同期される（実機で検証）。
2. 案件分離・ロールがサーバー側で強制され、権限外の記録へアクセスできない（セキュリティテスト）。
3. すべての操作（作成・編集・削除・検収・権限変更）が監査ログに記録される。
4. 検収済み記録の編集は差し戻し理由付きでのみ可能。
5. 端末紛失後、新端末でクラウドから復元できる（復旧テスト）。
6. 既存のローカルデータを失わずクラウドへ移行できる（移行テスト・後方互換）。
7. 1,000件/案件・同時100ユーザー程度で性能劣化がない（負荷テスト）。
8. CI（ユニット・契約・E2E・セキュリティ）がすべて成功し、リリース手順が整備されている。

## 11. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| 同期競合によるデータ取り違え | 高 | conflict 状態の明示と人間選択（自動上書き禁止） |
| 権限設定ミスによる案件間の情報漏えい | 重大 | API 側強制＋定期監査テスト（ペネトレーション含む） |
| 現場での通信コスト・電池消費 | 中 | 差分同期・写真の圧縮・同期スケジュール設定 |
| Entra ID ゲスト（協力会社）管理の複雑化 | 中 | 案件単位のゲスト招待と有効期限 |
| 既存ローカルデータとの整合 | 高 | sync_version ベースの移行と後方互換テスト |
| コストの不確実性（Neon/R2/Workers） | 中 | PoC での実測と月次コスト監視 |
| 公共成果品要件との境界 | 高 | 本スコープ外と明示し、Phase 4 の別プロジェクトとする |
