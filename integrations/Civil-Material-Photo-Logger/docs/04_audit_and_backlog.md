### ⚠️ 基盤方針との差異（重要）

上位方針（組織・グローバル `CLAUDE.md`）は **Cloudflare（Pages/Workers）+ Neon PostgreSQL を本番基盤**とする Web サービスを想定している。
本プロジェクトは **完全オフライン・端末内ローカル保存の iOS ネイティブアプリ**であり、次が構造的に適用できない。

| 上位方針の項目 | 本プロジェクトでの扱い |
|---|---|
| Cloudflare Pages / Workers デプロイ | **適用外**（Web フロント・Worker が存在しない） |
| Neon PostgreSQL / migration | **適用外**（DB を使用しない。端末内 JSON ファイル保存） |
| custom domain / 公開 DNS | **適用外** |
| Preview / staging 環境 | **適用外**（配布経路は TestFlight → App Store） |
| production smoke test / health check | **読み替え必要**（TestFlight ビルドでの実機確認へ） |

したがって本プロジェクトの「本番リリース」は **App Store Connect / TestFlight への配布**を指す。
これは**人間（Apple ID 保有者）の操作を必須**とし、Claude Code から自律実行できない。この点は §7 の判定に直結する。

### G-01 【P2】ダークモードで配色が画面ごとに割れる

| 項目 | 内容 |
|---|---|
| 根拠 | `AppColors.swift` の全 11 トークンが `Color(hex:)` による**固定 sRGB 値**。アプリ全体で `colorScheme` の参照が **0 件**。一方で `SettingsView` / `RecordFilterSheet` は `Form` / `List` と既定色に依存しており、**システム側でダークへ反転する** |
| 影響 | ダークモードにすると、**ブランド配色の画面（ホーム・CSV 出力・案件集計・材料傾向）はライトのまま、システム標準の画面（設定・絞り込みシート）はダークになる**。画面遷移のたびに明暗が切り替わり、統一感が失われる |
| 対応 | (a) `Color(light:dark:)` 相当のアダプティブトークンへ移行、または (b) `.preferredColorScheme(.light)` でライト固定を明示 |
| 効果 | 中 |
| 工数 | (a) 中（トークン定義 + 全画面の目視確認） / (b) 小（1 行） |
| リスク | (a) 全画面の見た目が変わるため視覚確認が必須。**本開発機（Linux）では検証不能** |
| 依存 | なし |
| 受入条件 | ダークモードで全画面の配色が一貫し、テキストと背景のコントラスト比が **WCAG AA（4.5:1）以上**であること。実機またはシミュレータのスクリーンショットで確認 |
| 判定 | **(b) を実施済み**（暫定・明示的なライト固定）。(a) は**バックログ（人間による視覚確認が必須）** |

> ⚠️ **当初の評価を修正した。** 「既定色のテキストが白背景の上で白文字になりうる」と見立てたが、実コードを確認したところ、ブランド配色の画面では `Text` にほぼ全て `AppColors.*` の前景色が明示されており（`RecordCardView` / `CSVExportView` などで確認）、システム既定色に依存する箇所は **2 件のみ**（`AccordionSectionView.swift:39`、`RecordCardView.swift:27`）。
> 逆に `SettingsView` / `RecordFilterSheet` は `AppColors` の濃色文字を使っておらず、システム既定色に任せているため単体では破綻しない。
> したがって**可読性の破綻（P1）ではなく、画面間の配色不統一（P2）**が正しい評価である。

### G-02 【P1】保存先確保に失敗したときのデータ消失が無言 — ✅ **本 PR で対応済み**

| 項目 | 内容 |
|---|---|
| 根拠 | （対応前）`MaterialPhotoLoggerApp.swift:11-17`。`JSONRecordStore.makeDefault()` が失敗すると `FileManager.default.temporaryDirectory` へフォールバックする。`Logger.fault` に「再起動でデータ消失」と記録されるが、**利用者へは何も表示されない** |
| 影響 | 記録は正常に保存できたように見えるが、iOS が一時ディレクトリを回収した時点で**全件消える**。写真台帳は監査証跡であり、静かに消えるのは最も避けるべき挙動 |
| 対応 | フォールバック時にフラグを立て、PR #82 で導入済みの `DataRecoveryBanner` と同じ仕組みで警告を常時表示する |
| 効果 | 大（発生時の被害が全損） |
| 工数 | 小（フラグ 1 つ + 既存バナーの再利用） |
| リスク | 小。既存の警告表示基盤を使うため新規の設計判断が不要 |
| 依存 | PR #82（マージ済み） |
| 受入条件 | 恒久保存先の確保を失敗させたとき、**退避した事実が呼び出し側へ伝わり、利用者に見える形で警告が出る**こと |
| 判定 | ✅ **対応済み**（本 PR） |

> 発生確率は極めて低い（iOS で Application Support が取得できないのは異常事態）。ただし発生時の被害が全損であり、対策コストが小さいため P1 とした。

**対応内容**：退避の判定を Core 層の `RecordStoreLocator` へ移し、`usedTemporaryFallback` として戻り値に載せた。App 層（SwiftUI）には自動テストの実行基盤がなく（G-07）、この分岐は「起動時にしか通らず、失敗時にしか通らない」二重に検証しづらい経路だったため、**バグの本体である判断部分を Linux でテストできる Core へ寄せた**。退避中は `TemporaryStorageBanner` を `RootView` に常時表示する（ホーム画面ではなくルートに置くのは、保存先の退避がアプリ全体の状態であり、ホーム以外の画面から使い始めても同じ危険があるため）。他の 2 つのバナーと異なり**閉じるボタンは置かない** — 一度閉じられると、以後の記録が全て消える前提で行われてしまう。

> ⚠️ **受入条件の当初案からの変更**：「ViewModel 層の単体テストで検証」としていたが、ViewModel テストターゲット自体が存在しない（G-07）。テストターゲットの新設は XcodeGen の設定変更を伴い、本開発機（Linux）ではコンパイル検証できないため、**判定ロジックを Core へ移して Linux で検証する**方式へ変更した。画面へのバナー表示そのものは CI の `iOS Simulator Build` による型検査のみで、**視覚確認は NOT RUN**。
