## 📌 1. モジュール概要

安全・品質管理モジュールは **安全チェック（SafetyCheck）** と **品質検査（QualityInspection）** の2エンティティで構成され、是正ワークフロー（指摘 → 対応 → 検証 → 完了）を担う。safety チェック `overall_result=NG` 時は BackgroundTask でコンプライアンスチェックを自動実行する（労働安全衛生法 第3条 連携）。

### 実装サマリ

| 種別       | 実体                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| 画面       | `frontend/src/pages/safety/`（安全チェック一覧・品質検査）                 |
| API        | `backend/app/api/v1/routers/safety.py` — 安全チェック CRUD / 品質検査 CRUD |
| テーブル   | `safety_checks` / `quality_inspections`（`backend/app/models/safety.py`）  |
| Legal 連携 | NG 時に `compliance_service` を自動実行（労働安全衛生法 第3条）            |

---

## 📌 2. 想定ユースケース

1. 現場の安全チェックリストを記録し、`overall_result`（OK/NG）で判定する。
2. NG 判定時にコンプライアンスチェックを自動実行し、是正処置を促す。
3. 品質検査の実施記録（検査項目・合否・検査員・是正内容）を管理する。
4. 是正依頼 → 対応 → 検証 → 完了のワークフローを管理する。

## 📌 3. ISO 別 要求マッピング

### 3.1 ISO 9001（品質マネジメント）

| ISO 要求（要約）               | システム機能へのマッピング                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 10.2 不適合・是正処置          | `QualityInspection` の是正ワークフロー（指摘 → 対応 → 検証 → 完了）が 10.2 の「検出 → 是正 → 再発防止」に対応 |
| 8.6 製品・サービスのリリース   | 品質検査（`quality_inspections`）による中間・完成検査記録                                                     |
| 8.5.1 製造・サービス提供の管理 | 安全チェック + 品質検査を工事の節目で実施する管理基盤                                                         |

**自分の言葉で**: 品質検査の「NG → 是正指示 → 是正確認」ワークフローが ISO9001 の是正処置手順そのもの。判定根拠と是正内容が記録される点が重要。

### 3.2 ISO 14001（環境マネジメント）

| ISO 要求（要約）              | システム機能へのマッピング                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------- |
| 10.2 不適合・是正処置（環境） | 安全チェックに環境不適合事象（廃棄物不適切処理・排水漏れ等）を記録し、是正処置管理 |

**自分の言葉で**: 安全チェックは安全衛生だけでなく環境不適合の記録にも転用できる。ただし環境専用項目は未実装のため `overall_result` の NG 理由に自由記述で対応する現状。

### 3.3 ISO 45001（労働安全衛生）

| ISO 要求（要約）                                   | システム機能へのマッピング                                                       |
| -------------------------------------------------- | -------------------------------------------------------------------------------- |
| 6.1 リスク及び機会への取組み（リスクアセスメント） | `SafetyCheck` の各チェック項目が現場リスクの評価記録になる                       |
| 10.2 インシデント・不適合・是正処置                | NG 判定 → 是正処置ワークフロー + compliance 自動チェック（労働安全衛生法 第3条） |
| 9.1 安全パフォーマンスの監視                       | OK/NG 集計で安全パフォーマンスを定量評価可能                                     |
| 4.2 利害関係者の要求事項                           | 下請・協力会社の安全管理を発注者視点で記録                                       |

**自分の言葉で**: `overall_result=NG` 時の自動コンプライアンスチェック連携が ISO45001 の「インシデント発生 → 即応」プロセスを実装している。これは compliance モジュールとの強い連携で実現している ServiceHub 固有の強み。

## 📌 4. アクセス制御の現状

| エンドポイント                              | アクセス制御                                                              | 状態                                            |
| ------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------- |
| `POST /projects/{id}/safety-checks`         | `assert_project_access`                                                   | ✅ write 保護                                   |
| `PUT /projects/{id}/safety-checks/{cid}`    | `assert_project_access`                                                   | ✅                                              |
| `DELETE /projects/{id}/safety-checks/{cid}` | service の複合キー検証（`resource.project_id != project_id → 404`）で防御 | ✅ Codex 対抗レビューで false positive 検証済み |
| `GET /projects/{id}/safety-checks`          | `require_roles` のみ                                                      | 📋 VIEWER 横断=製品意図 / Issue #239            |
| `GET /projects/{id}/quality-inspections`    | `require_roles` のみ                                                      | 同上                                            |

> ℹ️ safety の delete は service 層で `safety_check.project_id != path_project_id` を検証（複合キー）のため、path-resource mismatch IDOR は成立しない（PR #236 Codex 対抗レビューで検証済み）。
