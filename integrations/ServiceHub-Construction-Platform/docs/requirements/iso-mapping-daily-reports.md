## 📌 1. モジュール概要

日報は現場で毎日発生する作業実績・環境情報・安全確認を記録する**現場一次情報の発生源**である。上層（業務アプリ）として機能しながら、その一次データ性から中層（現場データ）の入口でもある。

### 実装サマリ

| 種別       | 実体                                                                                                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 画面       | `frontend/src/pages/reports/`（一覧・作成・詳細）                                                                                                                             |
| API        | `backend/app/api/v1/routers/daily_reports.py` — GET/POST/PUT/DELETE                                                                                                           |
| テーブル   | `daily_reports`（`backend/app/models/daily_report.py`）                                                                                                                       |
| 主要カラム | `project_id` / `report_date` / `weather` / `temperature` / `worker_count` / `work_content` / `safety_check` / `safety_notes` / `progress_rate` / `issues` / `status` / 監査列 |
| Legal 連携 | 日報作成時に `legal_evidence` を自動記録（BackgroundTask — 建設業法 第26条の4）                                                                                               |

---

## 📌 2. 想定ユースケース

1. 現場担当者が毎日の作業内容・従事人数・進捗率・気象条件を記録する。
2. 安全確認実施の有無（`safety_check`）と特記事項を記録し、安全活動の証跡とする。
3. 日報を承認ワークフロー（DRAFT → SUBMITTED → APPROVED）で管理する。
4. 日報作成と同時に、法的証跡（`legal_evidence`）として自動的に証跡タイムラインへ記録する（建設業法 第26条の4 工事記録保存義務への対応）。

## 📌 3. ISO 別 要求マッピング

### 3.1 ISO 9001（品質マネジメント）

| ISO 要求（要約）             | システム機能へのマッピング                                                     |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 8.5.2 識別・トレーサビリティ | `report_date` + `project_id` + `created_by` で工事実績のトレーサビリティを確保 |
| 7.5 文書化した情報の管理     | 承認ワークフロー（status）+ 監査列で記録の作成・承認・変更履歴を管理           |
| 9.1 監視・測定・分析         | `worker_count` / `progress_rate` / `issues` で工事進捗を数値で把握             |

**自分の言葉で**: 「いつ・誰が・どの工事で・何をしたか」を日単位で記録し、承認ワークフローで信頼性を担保することが ISO9001 のトレーサビリティ要求に対応する。

### 3.2 ISO 14001（環境マネジメント）

| ISO 要求（要約）                   | システム機能へのマッピング                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------------- |
| 9.1 環境パフォーマンスの監視・測定 | `weather` / `temperature`（気象条件）が環境影響記録の基礎データ                                     |
| 8.1 運用の計画と管理（環境側面）   | **専用の環境影響入力（騒音・廃棄物・燃料）は未実装**。`work_content` に自由記述として入力可能なのみ |

**自分の言葉で**: 気象データを記録する基盤はあるが、騒音・廃棄物量・燃料消費量の構造化入力は将来拡張。定量的な環境パフォーマンス監視には専用フィールドの追加が必要。

### 3.3 ISO 45001（労働安全衛生）

| ISO 要求（要約）                    | システム機能へのマッピング                                                              |
| ----------------------------------- | --------------------------------------------------------------------------------------- |
| 9.1 安全パフォーマンスの監視・測定  | `safety_check`（bool）で毎日の安全確認実施有無を記録                                    |
| 10.2 インシデント・不適合・是正処置 | `safety_notes` に安全特記事項・ヒヤリハットを記録                                       |
| 8.1 危険源の除去と安全リスクの低減  | `issues`（課題）欄で当日の安全上の問題を記録し、safety モジュールへエスカレーション可能 |

**自分の言葉で**: `safety_check` は毎日の安全確認の客観的記録として機能する。ただし boolean 1 フィールドのため「何を確認したか」の詳細は `safety_notes` の自由記述に依存しており、IS045001 の詳細なリスクアセスメント記録としては safety モジュールが補完する。

### 3.4 ISO 19650（BIM による情報マネジメント）

| ISO 要求（要約）                 | システム機能へのマッピング                                                                                                              |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 現場実績の情報コンテナへの紐付け | 日報作成時に BackgroundTask で `legal_evidence` へ自動記録（建設業法 第26条の4）。`project_id` + `report_date` が情報コンテナの識別基盤 |
| 情報の一貫性・改ざん防止         | 証跡記録は Fail-Closed の SHA-256 整合性検証（evidence モジュール）で保護                                                               |

**自分の言葉で**: 日報を「情報コンテナ候補」として legal_evidence に自動記録する設計は、ISO19650 の「現場実績の情報管理」を担う重要なブリッジ機能。証跡の SHA-256 検証が信頼性を担保。

## 📌 4. アクセス制御の現状（write 保護 / read 横断の製品方針）

| エンドポイント                      | アクセス制御                          | 方針                                                                                |
| ----------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------- |
| `POST /projects/{id}/daily-reports` | `assert_project_access`（write 保護） | ✅ write 側 IDOR 防止済み                                                           |
| `PUT /daily-reports/{id}`           | `existing.project_id` で二重検証      | ✅                                                                                  |
| `DELETE /daily-reports/{id}`        | `existing.project_id` で二重検証      | ✅                                                                                  |
| `GET /projects/{id}/daily-reports`  | `require_roles` のみ                  | 📋 **VIEWER 横断閲覧は製品意図**（監査用途）。Issue #239 で read スコープ設計を検討 |
| `GET /daily-reports/{id}`           | `require_roles` のみ                  | 同上                                                                                |

## 📌 5. 三層モデルでの実装層

| 層                        | 日報モジュールの役割                                           |
| ------------------------- | -------------------------------------------------------------- |
| 上層（`upper_business`）  | **本体**。作業実績・進捗・安全確認の業務記録                   |
| 中層（`middle_bim_data`） | BackgroundTask 経由で legal_evidence（現場一次情報）へ自動記録 |
| 下層                      | write は `assert_project_access` で IDOR 防止済み              |
