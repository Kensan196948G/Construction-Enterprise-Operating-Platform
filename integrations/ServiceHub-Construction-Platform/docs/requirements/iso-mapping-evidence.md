## 📌 1. モジュール概要

法的証跡タイムライン（`legal_evidence`）は、工事に関連するあらゆる法的証跡・工事記録を**改ざん耐性のある証跡コンテナ**として保存する。SHA-256 ハッシュによる Fail-Closed 整合性検証が特徴で、ServiceHub において ISO 適合性の中核を担う。

### 実装サマリ

| 種別      | 実体                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------- |
| 画面      | `frontend/src/pages/legal/LegalPage.tsx`（証跡タイムライン タブ）                                 |
| API       | `backend/app/api/v1/routers/legal/evidence.py` — GET timeline / POST / GET verify / GET entry     |
| テーブル  | `legal_evidence`（`backend/app/models/legal.py`）                                                 |
| 主要要素  | `project_id` / `source_type` / `title` / `event_date` / `description` / `content_hash`（SHA-256） |
| 自動記録  | 日報作成時に BackgroundTask で自動登録（建設業法 第26条の4）                                      |
| integrity | `verify_integrity()` — Fail-Closed: ハッシュ不一致・未設定・形式エラー → 改ざん判定               |

---

## 📌 2. 想定ユースケース

1. 工事に関するあらゆる法的出来事（契約締結・工期変更・安全事故・行政指導等）をタイムライン形式で記録する。
2. 日報作成を契機に作業実績を自動で証跡登録し、建設業法 第26条の4 の工事記録保存義務を担保する。
3. SHA-256 ハッシュで証跡の改ざん有無を検証し、記録の真正性を証明する。
4. コンプライアンスチェック（compliance モジュール）の監査証跡として参照される。

## 📌 3. ISO 別 要求マッピング

### 3.1 ISO 19650（BIM による情報マネジメント）— 最重要

| ISO 要求（要約）          | システム機能へのマッピング                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------- |
| 情報コンテナの管理        | `legal_evidence` 各レコードが情報コンテナに相当。`project_id` + `source_type` + `event_date` が識別基盤 |
| 情報の完全性（integrity） | `content_hash`（SHA-256）+ Fail-Closed `verify_integrity()` が情報の真正性を担保                        |
| 情報のステータス管理      | **Status コード（S0-S7/A1-An）の完全実装は未実装**。`source_type` で情報種別を分類するのみ              |
| CDE への情報集積          | `GET /{project_id}/timeline` でプロジェクト単位の証跡タイムラインを提供。CDE の「共有ゾーン」機能に相当 |

**自分の言葉で**: `legal_evidence` は ServiceHub における「情報コンテナ」の実装として最も成熟している。SHA-256 による改ざん検知は ISO19650 の情報整合性要求を技術的に担保する。ただし ISO19650 が規定する Status コード体系（S0〜S7、承認フロー）は未実装で、証跡の「承認段階」の管理は将来拡張。

### 3.2 ISO 9001（品質マネジメント）

| ISO 要求（要約）                             | システム機能へのマッピング                                                         |
| -------------------------------------------- | ---------------------------------------------------------------------------------- |
| 7.5.3 文書化した情報の管理（保護・変更防止） | SHA-256 Fail-Closed 整合性検証で記録の改ざんを検知。ソフトデリートで誤削除を防止   |
| 8.5.2 識別・トレーサビリティ                 | `project_id` + `event_date` + `source_type` で工事記録の完全トレーサビリティを実現 |

**自分の言葉で**: ISO9001 が求める「文書化した情報の保護」を、SHA-256 ハッシュという技術的手段で担保している点が ServiceHub の強み。改ざんが検知できない限り証跡として信頼できる。

### 3.3 ISO 14001 / 45001（環境・安全衛生）

| ISO 要求（要約）         | システム機能へのマッピング                                                     |
| ------------------------ | ------------------------------------------------------------------------------ |
| 環境・安全事故の記録管理 | `source_type` に環境事故・安全インシデントを設定して証跡記録                   |
| 是正処置の記録保持       | 是正実施の証跡を `legal_evidence` に登録し、コンプライアンスチェック経由で参照 |

### 3.4 ISO/IEC 27001（情報セキュリティ）

| ISO 要求（要約）                                | システム機能へのマッピング                              |
| ----------------------------------------------- | ------------------------------------------------------- |
| A.8.11 データマスキング / A.8.12 データ漏洩防止 | —                                                       |
| A.8.15 ログ取得 / A.8.16 監視活動               | `legal_evidence` への操作は全て `audit_log` に記録      |
| 情報の完全性（A.5.9）                           | `content_hash` による改ざん検知が情報完全性の技術的制御 |

### 3.5 J-SOX（内部統制）

| ISO 要求（要約）       | システム機能へのマッピング                                                        |
| ---------------------- | --------------------------------------------------------------------------------- |
| 証跡の保全・改ざん防止 | SHA-256 Fail-Closed でハッシュ不一致 → 改ざん判定。証跡の法的有効性を技術で担保   |
| 監査証跡               | `GET /{project_id}/timeline` で監査人が一覧取得可能。`GET /entry/{id}` で個別検証 |

**自分の言葉で**: J-SOX の内部統制で最も重要な「証跡の改ざん防止と監査可能性」を、SHA-256 ハッシュ + Fail-Closed 設計で実現している。これは ServiceHub 固有の実装的強みである。

## 📌 4. アクセス制御の現状（全エンドポイント最厳格）

| エンドポイント               | アクセス制御                           | 状態             |
| ---------------------------- | -------------------------------------- | ---------------- |
| `GET /{project_id}/timeline` | `assert_project_access`（read も保護） | ✅ 最厳格        |
| `POST /{project_id}`         | `assert_project_access`                | ✅               |
| `GET /{project_id}/verify`   | `assert_project_access`                | ✅               |
| `GET /entry/{evidence_id}`   | `evidence.project_id` で二重検証       | ✅ IDOR 二重防護 |

evidence は全エンドポイント（read を含む）で `assert_project_access` を適用する**最厳格モデル**であり、contracts（get/update/analyze は二重防護）や daily_reports/safety（write のみ）とは異なる。これは法的証跡の性質（改ざん・漏洩が法的リスクに直結）を反映した設計方針。

## 📌 5. 現状ギャップと将来拡張（ISO19650 完全準拠への道筋）

| 機能                         | 現状                       | 将来拡張                                                |
| ---------------------------- | -------------------------- | ------------------------------------------------------- |
| Status コード（S0-S7/A1-An） | 未実装                     | 証跡の承認段階を ISO19650 準拠の Status で管理          |
| Revision 管理                | 未実装                     | 証跡の版管理と版間差分追跡                              |
| 分類・命名規則               | `source_type` での簡易分類 | ISO19650 情報コンテナの完全命名規則（OIR/PIR に基づく） |
| 3D モデル連携                | 未実装                     | BIM/CIM との情報コンテナ紐付け                          |

## 📌 6. 三層モデルでの実装層

| 層                        | 証跡台帳モジュールの役割                                                |
| ------------------------- | ----------------------------------------------------------------------- |
| 中層（`middle_bim_data`） | **本体**。Information Container の実装。SHA-256 で改ざん耐性を担保      |
| 上層との接点              | 日報・安全・コンプライアンス等の上層イベントを証跡として吸収            |
| 下層との接点              | `audit_log`（下層）に全操作を記録。`assert_project_access` で IDOR 防止 |
