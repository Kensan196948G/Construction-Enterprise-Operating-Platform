## 📌 1. モジュール概要

案件管理（Projects）は工事案件のライフサイクル（受注 → 計画 → 施工 → 完了）を管理する**統合業務基盤の中核エンティティ**である。日報・原価・安全・契約・証跡など他の全モジュールが `project_id` で紐付く親エンティティであり、ISO 適合の起点となる。

### 実装サマリ

| 種別       | 実体                                                                                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 画面       | `frontend/src/pages/projects/ProjectsPage.tsx`（一覧）/ `ProjectDetailPage.tsx`（詳細 + タブ）                                                                                                         |
| API        | `backend/app/api/v1/routers/projects.py` — GET/POST/PUT/DELETE `/projects`、GET `/{id}/contracts`、GET `/{id}/legal-risks`                                                                             |
| テーブル   | `projects`（`backend/app/models/project.py`）                                                                                                                                                          |
| 主要カラム | `project_code` / `name` / `client_name` / `site_address` / `status` / `start_date` / `end_date` / `budget` / `manager_id` / 監査列（`created_at` `updated_at` `deleted_at` `created_by` `updated_by`） |

---

## 📌 2. 想定ユースケース

1. 発注者から受注した工事案件を登録し、工事コード（`project_code`）・現場・工期・予算・担当（manager）を管理する。
2. 案件のステータス（計画 → 施工中 → 完了）を遷移させ、工程を可視化する。
3. 案件に紐付く契約・日報・原価・安全記録・法的証跡を一元管理する。
4. 案件単位で法的リスク（工期遅延・契約リスク）を評価する。
5. ソフトデリート（`deleted_at`）で論理削除し、監査証跡を保全する。

## 📌 3. ISO 別 要求マッピング

### 3.1 ISO 9001（品質マネジメント）

| ISO 要求（要約）                               | システム機能へのマッピング                                                                                     |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 8.1 運用の計画と管理                           | `status`（PLANNING/IN_PROGRESS/COMPLETED）+ `start_date`/`end_date` による工程計画と進捗管理                   |
| 8.2 製品・サービス要求事項のレビュー（受注前） | `client_name`（発注者）+ 契約紐付け（`/{id}/contracts`）で受注内容を記録・レビュー                             |
| 7.5 文書化した情報の管理                       | 監査列（`created_by`/`updated_by`/`updated_at`）+ ソフトデリート（`deleted_at`）で記録の作成・変更・保持を管理 |
| 9.1 監視・測定・分析                           | `/{id}/legal-risks` で案件単位のリスク評価を可視化                                                             |

**自分の言葉で**: 案件の「計画 → 実行 → 完了」を status と工期で管理し、誰がいつ作成・変更したかを監査列で残すことが、ISO9001 の「計画的な運用」と「記録管理」の基盤になる。

### 3.2 ISO 14001（環境マネジメント）

| ISO 要求（要約）     | システム機能へのマッピング                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 6.1.2 環境側面の決定 | `site_address`（現場）を起点に、案件別の環境側面（騒音・廃棄物・排出）を識別する基盤。**専用入力は未実装（将来拡張）** |

**自分の言葉で**: 現状は現場住所までしか持たず、案件別の環境側面の構造化記録は将来拡張。daily_reports と連携した環境影響記録が次の一手。

### 3.3 ISO 45001（労働安全衛生）

| ISO 要求（要約）             | システム機能へのマッピング                                                                |
| ---------------------------- | ----------------------------------------------------------------------------------------- |
| 6.1 リスク及び機会への取組み | `project_id` で `safety` モジュール（安全チェック・是正）と紐付き、案件別リスク評価を実現 |
| 8.1 運用の計画と管理         | 案件の工期（`start_date`/`end_date`）に沿った安全計画                                     |

**自分の言葉で**: 案件が safety モジュールの親になることで、「どの工事で・いつ・どんな安全リスクがあったか」を案件単位で追える。

### 3.4 ISO 55001（アセットマネジメント）

| ISO 要求（要約）             | システム機能へのマッピング                                                                                        |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| アセットのライフサイクル管理 | `budget`（予算）+ `status` + 工期で、案件をライフサイクルでトラッキング。原価（`costs`）と連携した LCC は部分実装 |

**自分の言葉で**: 案件を「資産化対象」と捉え、予算とライフサイクルで管理する素地はあるが、ライフサイクルコスト（LCC）の本格管理は costs モジュールとの連携深化が必要。

### 3.5 ISO 19650（BIM による情報マネジメント）

| ISO 要求（要約）                               | システム機能へのマッピング                                                                   |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| プロジェクト情報の識別・命名規則               | `project_code`（一意識別子）が Information Container の命名・分類の起点                      |
| 責任主体の明確化（Appointing/Appointed Party） | `client_name`（発注者＝Appointing Party 相当）+ `manager_id`（受注側責任者）                 |
| プロジェクト情報要求（PIR）                    | 案件メタデータ（name/client/期間）が PIR の基礎。**CDE 連携・3D モデルは未実装（将来拡張）** |

**自分の言葉で**: `project_code` が将来の CDE（Common Data Environment）での情報コンテナ命名の核になる。現状は識別子と責任主体までで、CDE 本体は中層の将来拡張。

## 📌 4. 三層モデルでの実装層

| 層                            | 案件管理の役割                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------- |
| 上層（`upper_business`）      | **本体**。案件ライフサイクル・工程・予算・責任者の管理                                  |
| 中層（`middle_bim_data`）     | `project_code` を CDE の情報コンテナ識別子として将来連携（未実装）                      |
| 下層（`lower_it_foundation`） | `manager_id` で auth/access_control と連携し、案件単位のアクセス制御（IDOR 防止）を担う |

## 📌 5. アクセス制御の現状とギャップ（ISO 27001 / J-SOX 観点）

案件は IDOR 防止（`assert_project_access`）の所有権スコープの基準（`manager_id`）を提供する。一方、案件配下の一部 read エンドポイントに未適用箇所がある。

| エンドポイント              | アクセス制御                          | 評価                                                                                                                            |
| --------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `POST/PUT/DELETE /projects` | RBAC（ロール制限）                    | ✅ 書き込みはロール制御                                                                                                         |
| `GET /projects`, `/{id}`    | RBAC                                  | 一覧・詳細はロール制御                                                                                                          |
| `GET /{id}/contracts`       | `require_roles(ADMIN/PM/VIEWER)` のみ | ⚠️ **`assert_project_access` 未適用** — 他プロジェクトの契約一覧（金額・AI リスクスコア込み）を閲覧できる read-side IDOR の疑い |
| `GET /{id}/legal-risks`     | `require_roles` のみ                  | ⚠️ 同上 — 他プロジェクトの法的リスク評価を閲覧できる疑い                                                                        |

> ⚠️ `GET /{id}/contracts` / `/{id}/legal-risks` は PR #236（IDOR 防止）の対象ファイル（projects.py 非対象）から漏れていた。VIEWER 横断閲覧が製品意図か、案件オーナーのみに絞るかは **Issue #239** で read スコープ方針として検討する。legal ドメイン（evidence/compliance/contracts router）は read も厳格化済みのため、projects 経由の契約 read との方針差を解消する必要がある。
